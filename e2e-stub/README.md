# E2E Stub Server

Lightweight Express server that simulates the backend API for end-to-end testing. Used by the `ui-integration-testing-nectar-auth` Playwright test suite.

## Purpose

Provides scenario-based API responses for testing middleware authentication and session management flows without requiring the actual backend API.

## Usage

### Standalone

```bash
node e2e-stub/server.js
```

Server starts on `http://127.0.0.1:18080`

### Docker Compose (Recommended)

The stub is included in the E2E test environment via Docker Compose:

```bash
cd ../ui-integration-testing-nectar-auth
docker-compose up
```

This automatically starts both the stub server and nectar dev server with proper networking.

## Endpoints

### `/accounts/bootstrap`
Session initialization endpoint. Returns user data and sets session cookie.

**Scenarios** (via `x-test-scenario` header):
- `bootstrap-authenticated` - Returns authenticated user session
- `bootstrap-anonymous` - Returns anonymous user session
- `bootstrap-rotated-cookie` - Rotates session cookie value
- `bootstrap-unchanged-cookie` - Returns same cookie value
- `bootstrap-failure` - Returns 500 error
- `bootstrap-network-error` - Destroys socket

### `/accounts/verify/:token`
Email verification endpoint. Validates verification tokens.

**Scenarios** (via `x-test-scenario` header):
- `verify-success` - Returns successful verification
- `verify-unknown-token` - Returns unknown token error
- `verify-already-validated` - Returns already validated error
- `verify-failure` - Returns 500 error
- `verify-network-error` - Destroys socket

### `/link_gateway/*`
Analytics endpoint for tracking abstract page views.

### `/search/query` (also `/v1/search/query`)
Search results endpoint. Facet requests (any `facet*` or `json.facet` param)
get an empty response. Otherwise the payload depends on the scenario header.

**Scenarios** (via `x-test-search-scenario`, falling back to `x-test-scenario`
if the former is absent — this lets a test pick an authenticated session via
`x-test-scenario` and a search scenario independently):
- default (no scenario) - Synthetic results generated by `search-docs.js`,
  `numFound: 10000`, titles `Synthetic result N`.
  `e2e/fixtures/search-results.ts` imports the same generator, so the two
  payloads cannot drift.
- `search-results` - The committed results fixture in `fixtures/`,
  `numFound: 25`, titles `E2E Result 01`…`25`. Generated from
  `src/mocks/search-scenarios.ts` with drift enforced by a vitest file
  snapshot.
- `search-empty` - The empty fixture (`numFound: 0`, `docs: []`)
- `search-error` - Returns a 500 error

Both result paths honour `start`/`rows` (capped at 500) and keep `numFound`
constant across pages, so pagination behaves like a real multi-page result set.

### `GET /vault/configuration/site_wide_message`
Returns a minimal 200 (an empty string). The real endpoint returns the
site-wide banner message; e2e doesn't need one.

### `GET /vault/user-data`
Returns a minimal 200 (`{}`). The app merges this over its own defaults.


### Test Instrumentation

#### `GET /__test__/calls`
Returns history of all API calls made to the stub server.

**Response:**
```json
{
  "calls": [
    {
      "endpoint": "/accounts/bootstrap",
      "scenario": "bootstrap-authenticated",
      "headers": { ... },
      "timestamp": 1234567890
    }
  ],
  "count": 1
}
```

#### `POST /__test__/reset`
Clears call history. Should be called in test `beforeEach` hooks.

## Fixtures

`fixtures/search-results.json` and `fixtures/search-empty.json` back the
`/search/query` route. Both are **generated**, not hand-written: they come
from `src/mocks/search-scenarios.ts` via a vitest `toMatchFileSnapshot` test
at `src/mocks/search-scenarios.test.ts`. Do not hand-edit the JSON — change
the scenario source and regenerate with:

```bash
npx vitest run src/mocks/search-scenarios.test.ts -u
```

The test fails on drift, so a hand-edit or a stale generator will be caught.

## Scenario Usage

E2E tests set the `x-test-scenario` header to control stub behavior:

```typescript
await page.setExtraHTTPHeaders({
  'x-test-scenario': 'bootstrap-authenticated',
});

await page.goto('http://127.0.0.1:8000/search');
// Nectar dev server calls stub with scenario header
```

## Relationship to MSW

For auth/session flows, the stub mirrors the scenario-based responses of the
MSW handlers in `src/mocks/handlers/accounts.ts`, so unit/integration and e2e
tests see consistent behavior.

For search, the two deliberately diverge. The stub serves the deterministic
fixtures described above, because e2e assertions need fixed, known data
(stable titles, bibcodes, and a fixed `numFound`) to check against. MSW's
`src/mocks/handlers/search.ts` stays faker-randomized with a new seed per
run, because its job is to make the dev-mode UI look populated with varied,
realistic-looking data, not to support deterministic assertions.
